## 为什么选择这个功能

浏览器调研经常同时打开许多标签页。逐个复制标题和地址成本较高，书签又不方便直接放进 Markdown 笔记。独立导出页提供可检查的快照，让用户决定何时复制或下载。

## 关键取舍

- 查询用导出页自身的 `windowId`，而不是最后获得焦点的窗口。用户切换窗口不应改变导出来源。
- 数据转换为纯函数，浏览器 API、DOM 和文件下载放在页面层，分别验证规则与真实浏览器行为。
- 只按完整 URL 去重。查询参数与片段可能决定不同内容，不擅自去掉。
- 输出前转义 Markdown / HTML，预览通过 `textarea.value` 展示。地址含用户名或密码时跳过；普通查询参数仍可能有敏感信息，因此分享前由用户检查。
- 浏览器下载使用 Blob，不新增 downloads 权限，不引入服务端。复制被拒绝时明确提示手动操作，不谎报成功。
- 测试发现安装时手动注入和声明式注入会竞争，导致同一页面有两个面板。内容脚本加入 isolated world 内的初始化标记，避免重复注册事件和 DOM。

## 验收方法与边界

1. Node 原生测试验证排序、不修改输入、去重切换、非法地址、带认证地址、片段保留及标题转义。
2. Playwright 的独立 Chromium 配置实际加载 Manifest V3 扩展，使用 127.0.0.1 合成页面，验证命令入口、窗口隔离与下载文件的实际字节内容。
3. UI 在桌面和 390px 窄屏截图，检查水平溢出。剪贴板成功 / 拒绝和 API 失败分支使用模拟，避免修改系统剪贴板；扩展加载、标签查询、命令入口和文件下载使用真实调用。

本次没有验证 Firefox、个人 Chrome 配置、Chrome 商店安装、超大规模标签页或整个上游项目的所有功能。新增页面没有服务端；无端口或后台服务需要维护。

## 面试复习问题

- 为什么 `currentWindow` 或最后聚焦窗口可能导致导出错窗？请结合 `getCurrent()` 与 `windowId` 的代码说明。
- Set 去重的时间与空间复杂度是什么？为何仍先按标签位置排序？
- 为什么 URL 不能直接当 Markdown 链接目标？标题中包含 `[]`、换行或 HTML 时如何处理？
- 为什么不能把点击下载按钮等同于下载成功？测试读取了哪些证据？
- 内容脚本重复注入会导致哪些用户问题？初始化标记保存在哪个执行世界？
- 下一步如何增加单个标签勾选、跨设备保存或持久化偏好，同时明确权限与隐私边界？
